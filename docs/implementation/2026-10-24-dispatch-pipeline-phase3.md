# 第三阶段：候选并行准备与多实例独立投递

日期：2026-10-24（Asia/Hong_Kong）。基线提交：`1a35a82`。

状态：`IMPLEMENTED / LOCAL-VALIDATED`。用户随后已要求实施；本提交完成并发流水线、本地验证及四个发送边界的独立进程强制终止恢复测试。真实机器验收和 p95 ≤100 ms 性能目标仍未完成，未推送或部署。

## 目标

RSS 返回新条目后立即登记持久候选并开始有界并行准备；每条候选准备好即可分配和发送，不等待整批完成。每个下载机独立发送、后台确认与对账。一个慢 torrent 或一个慢实例不能阻塞其他具备资源的任务。

“已分配”必须表示真实 hash、大小已验证，目标归属和容量预留已提交。界面不能把未提交的暂定选择显示成已分配。有限并发仍允许排队，但不允许全局锁覆盖远端等待。

## 实施前基线

`1a35a82` 已具备持久消费者、退避与重启恢复、长 RSS 间隔下独立消费重试、torrent 原文持久化、按来源和凭据隔离的缓存、最多四个独立上游组并行、30 秒新鲜观测选路缓存，以及发送前附属监控与历史工作的分离。继续复用这些能力。

本轮针对以下基线缺口完成改造（以下描述仅指 `1a35a82`）：

- `internal/schedulercycle/cycle.go` 同一 feed 逐条准备；RSS 抓取与消费仍共用周期。
- `internal/app/app.go` 投递由 ticker 唤醒；没有单条就绪后的即时通知。RSS 轮询时间目前在候选处理结束后记录。
- `internal/dispatchstage/stage.go` 共享 coordinator 锁覆盖整批投递；实例同步锁覆盖采集到 Add 回执落库的全过程。
- `MaxInflight=1` 混合计算发送中、等待确认、UNKNOWN 和 EXPIRED_UNKNOWN，阻碍无关任务进入实例。
- `ReserveAtomic` 读取可用余额并写预留，但未在同一事务扣减余额或重算最新债务；现有串行流程依赖发送前重算。
- 确认入口不接受 `ADD_SENT`，回执落库依赖原状态和 ACTIVE waiter；尚未支持观察与回执乱序。
- `RESERVED/NOT_STARTED` 虽能被启动恢复识别，现有 Stage 会跳过发送并仅处理过期，尚未形成可恢复的待发送队列。
- `EnsurePolicy` 仍在发送路径请求 qui 策略列表、保存并读回；缓存失效的组选路仍可能现场等待远端。

## 实施清单

### 1. 并发安全基础（开放并发前必须完成）

- [x] 在短事务内校验真实身份唯一归属、目标有效性和容量，原子占用预算并写入 Attempt、Reservation、SubmitIntent；事务内没有远程请求。
- [x] 统一预留、释放和后台投影的预算语义；后台刷新必须读取事务内最新债务，不能覆盖新预留或重复扣减。保留快照版本、容量版本和配置有效性检查。
- [x] 支持先观察到 hash、后收到回执：持久保存早到观测，按 attempt 合并事实；后到回执不回退已确认结果。单任务的暂不可确认不能阻断同实例其他确认。
- [x] 建立持久的分配到发送交接。进程内通知仅用于唤醒；重启/通知丢失可从数据库恢复，单个发送者领取任务，发送开始标记保证同一 attempt 不重发。
- [x] 排队过期或发送前规则禁用时，仅对可证明未发送的链进行安全取消/释放；STARTED、UNKNOWN 保留原归属和债务，不自动重投。

### 2. 拆分发现与准备

- [x] RSS 流程只负责抓取、解析、登记候选及轮询状态；候选处理交给独立有界 worker。
- [x] 单条准备完成、job 与制品持久化成功后立即通知分配器；不等待整个 feed 或整批候选完成。
- [x] 全局和单站点分别限制准备并发，继续遵守站点共享请求预算。RSS 请求频率与 torrent 准备并发分别控制，不能用并发绕过限流。
- [x] 下一次抓取基于实际 RSS 请求时间和既定间隔；保留 baseline、304、禁用 feed/site、跨 feed 独立评估和失败恢复语义。
- [x] 复用现有制品与请求合并，保留站点、source key、URL、凭据引用及 origin 边界；不能仅按 infohash 混用不同 tracker/passkey 的 torrent 原文。

### 3. 多实例独立发送

- [x] 将全局协调缩短为本地决策和原子预留；远端状态刷新和 Add 不占全局锁。
- [x] 每实例独立后台同步和有界发送器；失鲜实例暂停新分配，健康实例继续。缓存失效不在全局路径同步等待该实例。
- [x] 分开发送请求槽、待确认积压限制和 UNKNOWN 风险额度；HTTP 结束后的事实必须可靠落库，等待确认继续保留身份与容量。
- [x] 排名及时反映已预留量、待发送队列及占用槽，避免连续候选都使用旧负载。队首大种无合适空间时继续检查其他可投候选。
- [x] 连续失败或未知结果积压达到阈值时，暂停该实例新分配；不扩大为全局停止，不把同 hash 改投另一实例。
- [x] ticker 保留为恢复兜底，即时唤醒不成为唯一进度来源。

### 4. 策略预热与验收

- [x] 根据已启用规则的当前版本后台预热 qui 策略，预热成功前不允许相关任务分配/发送；按规则版本和实例复用，发现外部修改、禁用或过期时拒绝发送。当前使用后台轮询预热，未增加配置保存 API 的同步预安装步骤。
- [x] 发送前以本地可验证事实完成规则、profile、路径、状态新鲜度和目标版本复核；不以优化为由取消原有有效性检查。
- [x] 记录 RSS 收到、torrent 就绪、分配提交、Add 开始、Add 返回、hash 观察、下载字节增长的时间。区分接收请求、观察到任务、真正开始传输。
- [x] 完成故障与突发测试后，记录本地夹具结果和真实环境结果各自的范围。

## 验收清单

- [x] 30 条候选中一条准备阻塞 20 秒，其他就绪任务在其完成前开始发送，不按输入顺序等待。
- [x] A 的 Add 阻塞 20 秒，B/C 的发送继续推进；确认延迟不占普通发送槽。
- [x] 预算 100 GB、两个不同 hash 各需 60 GB 时，竞争预留最多允许一个成功；刷新、释放、重启后账本一致。
- [x] 同 hash 从多个 feed 或 worker 同时出现，只有一个活动投递归属；Add 超时/回执丢失不换机重投。
- [x] 早到 hash、迟到成功/失败回执、重复事件、确认事务失败和重启均正确收敛；已确认结果不回退。
- [x] 在预留后通知未消费、领取后发送前、STARTED 后回执前、回执落库后四个边界，以 `os.Process.Kill` 强制终止独立测试子进程，再重新打开其真实 SQLite 文件并执行启动恢复。未发送可恢复；可能已发送不重复请求。Windows 的进程强制终止已验证，Linux SIGKILL 与真实 qui 链路仍待实机验证。
- [x] 失鲜、禁用、空间不足、策略失效仅阻断对应目标/任务；队列有界，取消和截止时间生效。
- [x] 测量单条及整批尾部延迟，不以缓存命中或最快样本代表整条 RSS 链路。

当前准备总并发为 8、单站点和同 hostname 各 2、每实例 Add 并发为 2。通过下方本地模拟验证，尚未作为实机吞吐结论。健康目标、有容量和空闲发送槽时，“候选就绪到 Add 开始 p95 ≤100 ms”仍为未达标的工程目标；本轮整批 30 条测量包含排队、快照失效和重新校验，未单独证明这一理想子集达标。

## 实现说明

1. 迁移 `0021_dispatch_pipeline.sql` 新增 `dispatch_queue`、`pending_confirmations`、消费者发现/匹配事实及 `dispatch_pipeline_times`。预留、预算扣减、发送意图、waiter 和队列在同一 SQLite 写事务提交；交接写入失败全部回滚。后台容量刷新在事务内读取最新预留，释放后的余额由下一次安全投影恢复，避免重复返还。
2. RSS 发现有 4 个 worker，准备有 8 个 worker，每站点及同 hostname 最多 2 个准备任务；单次消费 45 秒期限、torrent HTTP 30 秒期限，复用原消费者租约和失败退避。RSS 与 torrent 共用 hostname 请求频率预算，但使用独立并发槽；重定向仍走目标限流及既有出站校验。已有来源、凭据和原文缓存隔离继续保留。
3. 分配器单条持有全局协调锁，仅操作本地制品、有效缓存和数据库，不等待远端。每实例两个发送 worker，持久队列恢复加即时通知推进。发送前重验规则 revision、启用状态、组成员、profile 有效期、路径、快照坐标、容量和策略；发送标记与出队在同一事务提交，并把确认基线和截止时间重置到实际发送时刻。
4. 每实例 `RESERVED + ADD_SENT + AWAITING_CONFIRMATION` 最多 32 条，HTTP 槽为 2，`UNKNOWN + EXPIRED_UNKNOWN` 达到 2 时暂停该实例新分配/发送。2 是暂停阈值，已有在途或后续确认超时仍可能使 UNKNOWN 超过 2。最近三个已返回请求连续为确定无副作用失败时，暂停该目标一分钟；不会释放或改投不确定任务。
5. `ADD_SENT` 期间的正向 hash 观测先持久保存，不提前关闭 waiter。回执后重放观测；确认事务失败可重试；重启把 STARTED 链转 UNKNOWN 后，即使下载机离线，也能重放已有有效正向证据。快照清理保留这些未合并证据引用的快照。单条确认错误不阻断其他 waiter。
6. 每实例后台同步发布 30 秒有效、不可变的观测。每次本地使用必须与数据库 READY 状态、generation/revision/digest 一致；同步失败会清空缓存。托管 qui 策略按规则版本缓存 30 秒，后台预热/读回，未变配置不重复保存。外部改动需要等待下一次观测，无法承诺在 TTL 窗口内即时发现。
7. 兼容边界：升级前已有 `RESERVED/NOT_STARTED` 且没有持久队列的旧链，不凭猜测重建请求，沿用保留至参与截止的处理。新建链才有完整交接数据；STARTED/UNKNOWN 永不通过队列自动重放。旧任务缺少制品时由后台补取、校验 hash/大小后冻结，不在全局锁内下载。
8. 时序视图记录首次 RSS 来源发现、原文持久化、预留、发送开始、回执落库、hash 观察及首次正向 downloaded 字节证据。它们是本地观测时间，不是 qB 精确接收或首字节时间；`downloading` 状态本身不算字节增长。未经历阶段为 NULL；旧记录不虚构回填；终态原文按原七日规则清理后 `torrent_ready_at` 可能为 NULL。
