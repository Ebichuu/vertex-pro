# 流水线第四阶段：隔离辅助故障与上游等待

本轮在 `f3ba5ae` 基础上修复评审中的前三项阻塞，并补齐回执保存恢复和策略缓存提前刷新。验证使用本地合成 RSS、torrent 与 qui HTTP 服务；没有连接真实下载机，也没有重新开启旧 RSS 批次。

## 已实现

1. **统计与投递分离**：启动和同步不再要求 `transfer-info` 成功。实例启用状态、完整快照、Profile、保存路径及容量仍是投递门槛；传输统计和策略停用同步改到独立 worker。监控报错保留上次样本及其时间，按原新鲜度规则显示过期；不会清空有效的投递依据。快照采集前获取控制信息和 preferences，减少新快照已落库却还在等网络的间隙。
2. **坏 RSS 条目隔离**：事务前逐条规范化；非法条目只写安全错误码及 feed/index，不记录原 URL。合法 sources 与 consumers 仍在同一事务中提交，数据库错误仍整批回滚，且不会返回虚假的成功计数。RSS 页面对这类情况显示“部分条目无效”。
3. **限流、并发和等待分开配置**：新增 `request_burst`（默认 4，范围 1–16）、`max_concurrent_preparations`（默认 8，范围 1–32）、`max_preparations_per_host`（默认 2，范围 1–8）。设置页及 API、校验、诊断和生成契约同步更新；保存后重启服务生效。
   - 每个 hostname 的 RSS、torrent、重定向共享严格滚动一分钟预算，默认仍为 30。令牌桶允许小规模突发，突发额度实际不超过分钟预算。
   - 预算大于 1 时，为 RSS 保留 1 次；已排队 RSS 优先于 torrent。并非绕过站点预算，也不改变 RSS 轮询周期。
   - 网络超时在取得许可后启动，每个重定向 hop 单独计时；重定向最多 10 跳。准备工作的总时限为 consumer 的 120 秒租约减 5 秒，并受其最终截止时间约束。极低预算下仍可能用尽工作时限，进入原有有界重试。
   - consumer 持久记录限流开始时间与累计毫秒，按 attempt 防止旧 worker 覆盖新状态。RSS 页面显示当前等待条数和本轮/待处理项累计等待秒数。任务准备完成前尚无 race job，因此这里展示在 RSS 行，尚未提供逐条 preparation 列表。
4. **回执落库恢复**：实例内保留已经取得但尚未提交的结果，每秒重试保存；保留原回执时间，不持有或重发 HTTP 请求。待处理链继续占用原预算。提交成功后，提前确认的 replay 仍交给持久确认协调器。进程退出丢失的内存回执继续由原启动恢复转为 UNKNOWN，不自动重投。
5. **策略缓存提前刷新**：20 秒开始后台刷新，30 秒硬过期；临时通信/数据库失败不会延长旧缓存期限，已确认的远端停用、修改、身份漂移立即使缓存失效。新规则 revision 不复用旧条目。

数据库增加迁移 `0022_preparation_limits.sql`；不重置 sources、consumer、任务归属或历史去重。新旧前端构建资源保持一致。

## 验证与测量

- `go test -p 2 ./... -count=1 -json`：106 个测试包通过，证据 `artifacts/pipeline-phase4-all-go.jsonl`。随后补充的实际 XML “29 正常 + 1 非法 enclosure URL”用例通过，确认 29 个 race job 正常创建；相关包另行复验。
- SQLite trigger 注入回执写入失败，覆盖成功、结果不明和明确未发送三类结果；故障解除后状态推进，原发送次数保持 1。持久队列删除后的恢复路径也通过。
- `transfer-info` 报错、一直阻塞均不阻断缓存读取和快照推进；三实例组测试从启动起持续返回 503，30 条任务仍全部确认。
- 前端 TypeScript 检查、Vite 构建通过；Vitest 25 文件、173 项通过。使用本地 Node 24.22.1，`node node_modules/vitest/vitest.mjs run --pool=threads --maxWorkers=2`。默认 pnpm 11 与仓库版本约束不符，未改全局环境；默认 fork 池出现 IPC channel closed，改用线程池完成验证。没有据此宣称本地完整 preflight 通过。
- `go vet ./...`、生成代码一致性、契约检查、仓库结构、许可证、149 项实施表检查通过。没有运行 race detector。

默认参数自动组选路夹具：30 条，三台容量分别可容纳 24/16/8 个任务；由策略选择目标，并非预先指定各 10 个；其中一个 torrent 响应延迟 20 秒，A 的首个 Add 回执延迟 20 秒。站点预算 30/min、burst 4、准备并发 8/2、同步间隔 10 秒。

本轮分配 10/12/8，无重复 Add；独立首轮为 11/11/8。分配受瞬时负载、预留和快照更新共同影响，不能解读为固定比例。首轮和全套均通过；消费者限流等待累计约 100 秒是多个任务等待之和，不是整批墙钟耗时。最后两份 torrent 受滚动分钟预算和 RSS 保留额度约束，需要等到约第 60 秒；本轮修改缩短首批等待，不承诺突破分钟预算。

600/min、200 ms 同步的原固定目标夹具继续通过，内部 ready→STARTED p95 为 22.085 ms，并新增 p95≤100 ms 的失败断言。默认配置组夹具该指标为 22.635 ms，但仅作样本记录。HTTP 接收时间与内部 STARTED 明确分开；下载增长由本地服务合成，以上不是 tracker/peer 下载速度，也不是真实双机验收。

追加容量上限断言后的最终组复测也通过：11/11/8，首/末 Add 到达约 21.133 ms/60.041 s，p95 35.125 ms；有一条 111.994 ms 尾样本，主要发生在预留后、STARTED 前。日志 `artifacts/pipeline-phase4-group-final.log`。这进一步说明毫秒级样本不能当作固定延迟保证。
