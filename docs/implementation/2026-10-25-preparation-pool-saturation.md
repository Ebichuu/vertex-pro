## 测量范围

测试入口为 `internal/app/preparation_saturation_test.go` 的 `TestPreparationPoolSaturation`，使用生产 `app.New`、真实 discovery/preparation worker、SQLite 和回环 HTTP。没有配置 qui、Add sender、真实 RSS、凭据或下载器。每组包含 H 的 8 条 torrent 和 K 的 1 条 torrent：

- 对照组：H 的 8 条任务来自同一个 RSS 来源。
- 满载组：H 的 8 条任务分散于四个 RSS 来源，每个来源 2 条。
- 两组都采用全局准备名额 8、每来源和实际 hostname 名额 2、每分钟请求预算 30、突发额度 4。
- RSS 来源使用不同回环 IP 的 hostname；不同端口不会被误当成不同 hostname。
- 确认 H 已有 2 个 HTTP 请求占槽后才开放 K 的 RSS。满载组还验证已有 8 个 consumer 被认领、6 个任务在等待许可。
- K 的 consumer 入库后，人为保持 H 阻塞最多 3 秒；K 若提前开始，则立即释放 H。记录 K 的 HTTP 到达时间，最终验证 9 个 consumer 全部 DONE、9 个准备 job 和 H 最大并发 2。

满载组中，H 释放前 K 的 `attempts=0`。H 释放后约 1.732 ms 收到 K 的 torrent HTTP 请求。两组最终都完成准备，没有发生死锁；但这不意味着慢 host 已经完全隔离。**等待 host 许可的任务仍占用上层准备名额，满载时会延迟其他 host 的新任务。** 这发生在分配和 Add 之前，不能据此说已发送给其他下载机的任务也被阻塞。

3 秒是注入的保持时长，不是等待上限。上述数据是一轮本地对照，不是真实站点或异地 qB 延迟；真实请求预算和同步采样仍影响端到端结果。

## 复现与判定

在仓库根目录运行，不需要本地 overlay 或私有文件：

```sh
go test ./internal/app -run '^TestPreparationPoolSaturation$' -count=1 -v
```

输出 `SATURATION_PROBE` JSON，包含每组认领数、等待许可数、K 是否提前开始及各段时间。测试断言保证有效对照、实际 host 并发上限、任务最终完成和关闭时连接释放；满载组的三秒等待属于记录的当前行为，不作为“必须保持缓慢”的断言。将来若改变准备池准入方式，应同时更新预饱和状态检查。

此夹具在普通测试中运行，`-short` 跳过带受控等待的测量，与既有 30 条长批次夹具保持一致；它不是新的速度通过门槛。原有固定参数 `ready → STARTED` p95 ≤100 ms 断言未改，已有 Linux race 的六包检测范围也未改。
