# UI-08 History Detail 设计

## 范围

在 `local-only` 边界内补齐 History Detail。页面不连接真实 API、数据库、qui、qB 或外部服务，不提供删除、暂停、恢复、reannounce 或重新 Add 操作。正式 Gate 仍停在 `BOOT-01`，因此 UI-08 完成后仍标记为 `IN_PROGRESS`。

## 方案选择

采用“详情投影 + 可注入加载器 + 路由 fixture”方案：

- 独立的前端详情模型只携带页面所需字段，避免组件理解后端状态机。
- `HistoryDetailPage` 接收 `jobId` 和异步加载器，负责加载、失败、重试与展示。
- `/history/$jobId` 默认注入确定性本地 fixture，保证开发和测试不产生外部调用。
- History 列表通过显式详情按钮进入详情路由。

未采用直接扩展 `GET /api/v1/jobs/{id}` 的方案，因为当前任务明确保持 `local-only`，后端详情合同还没有完整接入时间线、规则聚合和删除事实。也未把详情逻辑并入列表组件，以免列表和详情形成难以独立测试的耦合。

## 信息架构

普通视图按用户问题组织：

1. 当前或最后状态、来源、目标下载器与关键时间。
2. 最后累计上传量、下载量、分享率和观测时间。
3. 命中规则、胜出规则及最终分类、标签和保存路径。
4. 发现、准备、添加、确认、上传、删除的稳定时间线。
5. 删除已确认时，展示确认时间和用户可读的证据来源。

`Candidate`、`Placement`、`Reservation`、`Reflection`、`SubmitIntent`、`capacity epoch`、原始事件类型、revision 和 digest 只能出现在默认折叠的“高级诊断”区域。

## 状态与错误

- 加载期间显示详情骨架文本，不保留旧记录。
- 加载失败显示可访问错误提示和“重新加载”操作。
- 未提供上传量、分享率、删除确认或失败原因时显示“暂无数据”，不得把未知值序列化为零或成功。
- 删除后的记录继续展示最后已知传输数据与删除确认时间。
- 当前时间线是 UI-08 的最小用户投影；Tracker、Peer、首个上传和观测关闭等完整事件等待 HIS-03 详情 API 接线。

## 验收

- 组件测试覆盖摘要、规则聚合、时间线、删除保留、内部术语隔离和失败重试。
- 路由测试覆盖 `/history/$jobId` 可直接访问且不调用外部服务。
- 浏览器检查 390、1024、1440px，以及亮色和暗色主题；无横向溢出、文本遮挡或普通视图内部术语泄漏。
- 通过前端测试、类型检查、构建、Go 全量测试、`go vet`、代码生成检查、UTF-8/JSON/递归证据摘要检查。
